# P0 — Public Dashboard Functional Regression: Scheduled Data Must Never Break the Site

## Objective
Investigate and permanently prevent the reported regression where the public QuantBet Football dashboard appears broken after scheduled data publication.

This is an operational/public-surface blocker. A green GitHub Pages deployment is not sufficient evidence that the dashboard is functionally healthy.

## Audit evidence
Latest public deployment commit:
`68915e6d8232e9d3984de71819fd19f3fdf77e56`

Message:
`Update QuantBet signal classification observations`

Pages deployment completed successfully for this commit. The immediately preceding scheduled settlement watchdog and scheduled Strong Signal watchlist jobs also completed successfully.

The latest commit modifies generated/public data only:
- `data/intraday_signal_events.jsonl`
- `data/market_timing_snapshots.jsonl`
- `data/raw_api/2026-09-09.jsonl`
- `intraday_watchlist_state.json`
- `market_timing_metrics.json`
- `near_misses.json`

The commit does not modify frontend source. Therefore the current hypothesis is a generated-data/public-contract regression or data-volume/runtime issue, not a Pages build failure.

The preceding scheduled commit also changed a historical intraday alert from `PENDING` to `SKIPPED` for an alert from 2026-09-08. Historical state transitions must remain valid public data and must not be hidden by deletion.

## Required investigation

1. Reproduce the currently reported broken dashboard from the exact deployed `main` state.
2. Identify the exact view/component/data file that causes the failure.
3. Compare current generated datasets against the last known-good public state.
4. Validate every generated public JSON artifact against the actual frontend runtime contract.
5. Test `null`, empty arrays, missing optional fields, historical statuses (`PENDING`, `SKIPPED`, `SETTLED`, `VOID`, etc.), and large historical datasets.
6. Check whether `near_misses.json` growth can cause rendering, parsing, or performance failure.
7. Check whether `intraday_watchlist_state.json` rewrite/merge semantics can remove required records or alter expected shape.
8. Verify that each scheduled workflow only owns and mutates its canonical output; no workflow may overwrite another workflow's incompatible public state.
9. Verify atomicity/concurrency of generated-data publication and Git commits.
10. Add a frontend/public-data functional contract test that loads the exact generated datasets the way the dashboard does and verifies all required views render successfully.
11. Add regression tests for historical status transitions, including `PENDING -> SKIPPED`, without fabricating settlement or deleting evidence.
12. Add a pre-publication gate so a green Pages build cannot publish a dataset that fails the functional public contract.
13. Run the full contract test against a real scheduled-generated dataset before closing.

## Required views
At minimum validate:
- Overview
- Production
- Strong Signals
- Near Misses
- History

Also verify:
- lifecycle fields remain truthful;
- bookmaker identity remains valid;
- stale/unavailable states are rendered explicitly;
- empty collections do not crash the UI;
- malformed records cannot crash the entire page;
- mobile 320px+ remains usable;
- large history does not make the page unusable.

## History rule
**Do NOT throw history away.**

Historical evidence must remain persisted. If an old record is invalid for a current UI contract, introduce an explicit compatibility/normalization layer or explicit status classification. Never silently delete, overwrite with fabricated values, or hide historical evidence merely to make the dashboard green.

## Non-goals
- No blind rollback.
- No deletion/reset of generated history.
- No change to settlement mathematics.
- No change to Dixon-Coles/model mathematics.
- No change to calibration, de-vig, EV/edge, Kelly, risk, eligibility, bookmaker policy, lifecycle mathematics, or H2H.

## Acceptance criteria
- [ ] Exact current dashboard failure reproduced and root cause identified.
- [ ] Current generated datasets pass the frontend's real runtime contract.
- [ ] All required public views render successfully from scheduled-generated data.
- [ ] Historical data is preserved.
- [ ] Historical status transitions are explicitly supported.
- [ ] Large generated collections do not break rendering.
- [ ] Workflow ownership/concurrency cannot produce incompatible public state.
- [ ] Functional public contract test runs automatically before publication.
- [ ] A green Pages build cannot mask a failing public-data contract.
- [ ] Real scheduled-run evidence proves the fix.
- [ ] No model/strategy/risk/settlement changes were introduced.

## Definition of Done
The public dashboard is functionally healthy from the exact datasets generated by scheduled automation, not merely successfully deployed. Future generated-data regressions fail explicitly before publication, while historical evidence remains intact and auditable.
